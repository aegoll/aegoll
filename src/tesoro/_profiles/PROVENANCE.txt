Vendored AEGS profile manifests — package data, not a source of truth.

The canonical profiles live in the standard's own repository:

    https://github.com/tesoro-labs/aegs   ->   profiles/

They are copied here so `tesoro` can report conformance without a network call. A
profile is a conformance contract written by the standard; this package enforces one,
it does not define one.

  stablecoin-1.json
                VERTICAL, not a rung on the ladder. Extends aegs-2 and requires
                AMLAssessment at MUST_RECORD under PROF-6a, on the basis that the
                deployment class it names -- obliged entities settling in stablecoins --
                already meets that bar by licence. This package has no AML control, so it
                emits no assessments/aml key, so it DOES NOT CONFORM to this profile.
                That is the intended reading. A profile whose only claimants are the
                implementations that wrote it measures nothing.

Rules
-----
  1. Never edit a file in this directory. A profile change is a change to the standard,
     made in the `aegs` repository and copied down afterwards. Editing here would let
     this package claim conformance against a contract nobody else holds.

  2. CI fails when a vendored copy differs from the standard at the pinned commit, and
     the pin is raised deliberately. Same tool as the schemas:
     `python tools/check_schema_drift.py`.

Why the pin matters more here than for a schema
-----------------------------------------------
A stale schema makes validation wrong. A stale profile makes a *conformance claim*
wrong — and a conformance claim is the thing an auditor is meant to be able to rely on.
Adding a control at MUST_EXERCISE upstream is a major change: implementations that were
conformant stop being conformant, and a package still holding the old copy would keep
reporting a level it no longer reaches.
